# Система обслуживания клиентов банка

Система обслуживания клиентов банка — веб-приложение для сотрудников банка. Главная цель — быстро найти клиента, открыть его полную карточку и безопасно выполнить связанные с ним операции.

Проект реализуется как модульный монолит: основная бизнес-логика пишется на Java, серверный интерфейс — на Spring MVC и Thymeleaf, а Kotlin применяется для изолированных вспомогательных сервисов.

## Технологии

- Java 25
- Spring Boot, Spring MVC и Thymeleaf
- Spring Security
- Spring Data JPA / Hibernate
- PostgreSQL и Flyway
- Gradle и JUnit
- Jenkins CI/CD, systemd и Nginx для деплоя
- Kotlin для вспомогательных сервисов

## Основной функционал

Центральный объект системы — `Client`. Сотрудник начинает работу с поиска клиента или создания новой карточки.

### Обслуживание клиентов

- Регистрация нового клиента.
- Поиск по имени, персональному коду, телефону, e-mail или номеру счёта.
- Карточка клиента с личными данными, контактами, адресами и документами.
- Редактирование данных клиента.
- Статусы клиента: `ACTIVE`, `BLOCKED`, `REQUIRES_VERIFICATION`.
- Заметки сотрудника о клиенте.
- История изменений данных и аудит.

### Счета и операции

- Открытие текущих и накопительных счетов для клиента.
- Просмотр баланса и статуса счёта.
- Блокировка или закрытие счёта.
- Пополнение счёта и снятие денежных средств.
- Перевод между счетами.
- История операций клиента.
- Дневные или разовые лимиты на операции.

### Обращения клиентов

- Создание обращения: новая карта, изменение лимита, закрытие счёта или консультация.
- Статусы обращения: `NEW`, `IN_PROGRESS`, `COMPLETED`, `REJECTED`.
- История обращений в карточке клиента.

### Пользователи и права доступа

| Роль | Возможности |
| --- | --- |
| `ADMIN` | Управление сотрудниками и ролями, полный доступ, отчёты |
| `MANAGER` | Клиенты, счета, обращения и отчёты |
| `OPERATOR` | Поиск клиентов, обновление данных, операции по счетам |

## Пользовательский сценарий

```text
Авторизация сотрудника
        ↓
Поиск или регистрация клиента
        ↓
Карточка клиента
 ├── личная и контактная информация
 ├── счета и балансы
 ├── история операций
 ├── обращения
 └── заметки сотрудника
        ↓
Действие: изменение данных, открытие счёта, операция или обращение
        ↓
Валидация, проверка прав, сохранение и аудит
```

## Бизнес-правила

- Нельзя создать двух клиентов с одинаковым персональным кодом.
- Заблокированному клиенту запрещены финансовые операции.
- Счёт можно закрыть только при нулевом балансе.
- Снятие или перевод невозможны при недостатке средств.
- Денежные суммы хранятся в `BigDecimal`, а не в `double` или `float`.
- Каждое изменение данных и каждая операция создают запись в `AuditLog`.
- Перед выполнением действия проверяются роль и права сотрудника.
- Операция перевода должна быть транзакционной (`@Transactional`).

Назначение слоёв:

Контроллеры не используют JPA-сущности как модели HTML-форм. Для этого создаются DTO: `Form` для входных данных и `View` для отображения. Это разделяет ответственность классов и помогает соблюдать SOLID-принципы.

## Интерфейс на Thymeleaf

Thymeleaf позволяет не создавать отдельный frontend-сервис. Spring MVC-контроллер формирует модель данных и возвращает имя HTML-шаблона.

Основные страницы:

- `/login` — авторизация сотрудника.
- `/clients` — поиск и список клиентов.
- `/clients/new` — регистрация клиента.
- `/clients/{id}` — карточка клиента.
- `/clients/{id}/edit` — редактирование данных клиента.
- `/clients/{id}/accounts` — счета клиента.
- `/accounts/{id}/transactions/new` — финансовая операция.
- `/clients/{id}/requests` — обращения клиента.
- `/reports` — отчёты для менеджера или администратора.

## Вспомогательные сервисы на Kotlin

Kotlin не нужно использовать для критичной финансовой логики: код счетов и переводов остаётся в Java-модулях. Kotlin хорошо подойдёт для небольших независимых сервисов.

- `NotificationService` — уведомления об открытии счёта, переводе или блокировке. На первом этапе сервис может записывать уведомления в журнал.
- `ReportExportService` — экспорт отчётов по клиентам или операциям в CSV/Excel.
- `ClientDataMaskingService` — маскировка персональных данных в журналах, например `+371******12`.
- `ClientDataValidationService` — дополнительная валидация персонального кода, e-mail и телефона.
- `DailySummaryJob` — периодическая задача, собирающая число новых клиентов, операций и заблокированных счетов.

## Деплой через Jenkins на одной VM

Схема рассчитана на **Ubuntu Server 24.04 или 26.04 LTS с systemd**. Jenkins, его локальный Linux-агент, Spring Boot и существующая PostgreSQL находятся на одной VM. Nginx принимает запросы к домену банка на 80/443 и проксирует их на Spring Boot по `127.0.0.1:18080`. Jenkins может сохранить свой порт 8080.

### Подготовка VM

1. Направьте публичную A-запись домена банка на VM. При наличии AAAA проверьте также IPv6. Разрешите входящий TCP 80 (проверка домена при выпуске и продлении сертификата) и 443 (HTTPS). Порт 18080 должен быть свободен. Серверу нужен исходящий HTTPS к пакетам Ubuntu, Adoptium, Gradle, Maven и Let's Encrypt.
2. Создайте в Jenkins выделенный **локальный агент** с меткой `baltic-bank-vm`, одним executor и отдельным непривилегированным Unix-пользователем, например `bank-deploy`. Для запуска агента на этой же машине подходит inbound agent. Установите Git и Bash. Разрешите выполнение job на этом агенте только доверенным сборкам релизной ветки.
3. Один раз подготовьте систему. Из доверенного checkout на VM выполните команду **от имени пользователя агента через sudo**, например после входа под `bank-deploy`:

   ```bash
   sudo bash devops/deploy/provision.sh balticbank.duckdns.org goldydefault@gmail.com
   ```

   Скрипт установит JDK 25 (OpenJDK на 26.04, Temurin на 24.04), Nginx и Certbot, создаст unit приложения, выпустит сертификат и включит таймер продления. Если у пользователя агента уже есть неинтерактивный sudo для первичной установки, этот шаг выполнит стадия **Prepare host**. После подготовки агенту достаточно права на restart и stop одной службы. При изменении конфигурации provisioning, домена или email повторите команду с sudo. На сервере должны присутствовать бинарные файлы существующей PostgreSQL в `/usr/lib/postgresql/<версия>/bin`.
4. Подготовьте рабочую базу и роль приложения с правами на миграции Flyway. Перед первым обновлением существующей базы проверьте резервную копию.

### Настройка Jenkins

В Jenkins нужны плагины Pipeline, Git и Credentials Binding. Создайте credentials в папке job:

| ID | Тип | Значение |
|---|---|---|
| `baltic-bank-db-url` | Secret text | JDBC URL, например `jdbc:postgresql://127.0.0.1:5432/bank` |
| `baltic-bank-db` | Username with password | Пользователь и пароль рабочей PostgreSQL |

1. Добавьте Jenkinsfile и `devops/deploy/` в репозиторий. Создайте **Pipeline → Pipeline script from SCM → Git**, выберите доверенную ветку и путь `Jenkinsfile`. Для приватного репозитория отдельно задайте SCM credentials.
2. Нажмите **Build Now**. Домен и контактный email заданы в блоке `environment` файла `Jenkinsfile`. При смене контакта или домена обновите этот блок.
3. После успешного деплоя откройте `https://ВАШ-ДОМЕН/login/client` или `https://ВАШ-ДОМЕН/login/employee`.

### Сертификат

Certbot автоматически получает сертификат Let's Encrypt для указанного публичного домена через HTTP-01. Nginx перенаправляет HTTP на HTTPS. При продлении сертификата deploy hook перечитывает конфигурацию Nginx. Для внутреннего имени или VM, недоступной из интернета на порту 80, потребуется другой способ валидации (например, DNS-01 для публичного домена) либо сертификат внутреннего центра сертификации. Конфигурация проксирует приложение банка. Доступ к Jenkins на его собственном порту ограничьте административной сетью или VPN.

### Что делает pipeline

- Проверяет коммит с изолированной временной PostgreSQL, созданной на свободном локальном порту с одноразовым паролем. Выполняет `clean test bootJar` через Gradle Wrapper. Рабочие DB credentials привязаны только на стадии деплоя.
- Записывает JAR и файл `database.env` с правами 0600 в каталог релиза в `/opt/baltic-bank/releases/`. Секреты передаются между процессами через stdin. Файл нужен для автоматического старта через systemd после перезагрузки. Каталоги предыдущих релизов также содержат параметры подключения. При ротации пароля обновите Jenkins credentials и повторите деплой.
- Атомарно переключает ссылку `/opt/baltic-bank/current`, перезапускает службу и проверяет HTTP 200 страницы входа напрямую и через Nginx с проверкой TLS. На время старта одного экземпляра возможен короткий перерыв.
- Если проверка не прошла, пытается запустить предыдущий JAR с его параметрами подключения. При первой неуспешной установке останавливает службу. Уже применённые миграции базы не откатываются. Для несовместимой миграции потребуется отдельное восстановление базы.

Проверка состояния:

```bash
systemctl status baltic-bank.service
sudo journalctl -u baltic-bank.service -n 100
sudo nginx -t
systemctl list-timers certbot.timer
sudo certbot renew --dry-run
```
