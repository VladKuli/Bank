# Система обслуживания клиентов банка

Система обслуживания клиентов банка — веб-приложение для сотрудников банка. Главная цель — быстро найти клиента, открыть его полную карточку и безопасно выполнить связанные с ним операции.

Проект реализуется как модульный монолит: основная бизнес-логика пишется на Java, серверный интерфейс — на Spring MVC и Thymeleaf, а Kotlin применяется для изолированных вспомогательных сервисов.

## Технологии

- Java 25
- Spring Boot, Spring MVC и Thymeleaf
- Spring Security
- Spring Data JPA / Hibernate
- PostgreSQL и Flyway
- Gradle и JUnit
- Jenkins CI/CD, Docker Compose и Nginx для деплоя
- Kotlin для вспомогательных сервисов

## Основной функционал

Центральный объект системы — `Client`. Сотрудник начинает работу с поиска клиента или создания новой карточки.

### Обслуживание клиентов

- Регистрация нового клиента.
- Поиск по имени, персональному коду, телефону, e-mail или номеру счёта.
- Карточка клиента с личными данными, контактами, адресами и документами.
- Редактирование данных клиента.
- Статусы клиента: `ACTIVE`, `BLOCKED`, `REQUIRES_VERIFICATION`.
- Заметки сотрудника о клиенте.
- История изменений данных и аудит.

### Счета и операции

- Открытие текущих и накопительных счетов для клиента.
- Просмотр баланса и статуса счёта.
- Блокировка или закрытие счёта.
- Пополнение счёта и снятие денежных средств.
- Перевод между счетами.
- История операций клиента.
- Дневные или разовые лимиты на операции.

### Обращения клиентов

- Создание обращения: новая карта, изменение лимита, закрытие счёта или консультация.
- Статусы обращения: `NEW`, `IN_PROGRESS`, `COMPLETED`, `REJECTED`.
- История обращений в карточке клиента.

### Пользователи и права доступа

| Роль | Возможности |
| --- | --- |
| `ADMIN` | Управление сотрудниками и ролями, полный доступ, отчёты |
| `MANAGER` | Клиенты, счета, обращения и отчёты |
| `OPERATOR` | Поиск клиентов, обновление данных, операции по счетам |

## Пользовательский сценарий

```text
Авторизация сотрудника
        ↓
Поиск или регистрация клиента
        ↓
Карточка клиента
 ├── личная и контактная информация
 ├── счета и балансы
 ├── история операций
 ├── обращения
 └── заметки сотрудника
        ↓
Действие: изменение данных, открытие счёта, операция или обращение
        ↓
Валидация, проверка прав, сохранение и аудит
```

## Бизнес-правила

- Нельзя создать двух клиентов с одинаковым персональным кодом.
- Заблокированному клиенту запрещены финансовые операции.
- Счёт можно закрыть только при нулевом балансе.
- Снятие или перевод невозможны при недостатке средств.
- Денежные суммы хранятся в `BigDecimal`, а не в `double` или `float`.
- Каждое изменение данных и каждая операция создают запись в `AuditLog`.
- Перед выполнением действия проверяются роль и права сотрудника.
- Операция перевода должна быть транзакционной (`@Transactional`).

Назначение слоёв:

- `domain` — бизнес-объекты и правила предметной области.

Контроллеры не используют JPA-сущности как модели HTML-форм. Для этого создаются DTO: `Form` для входных данных и `View` для отображения. Это разделяет ответственность классов и помогает соблюдать SOLID-принципы.

## Интерфейс на Thymeleaf

Thymeleaf позволяет не создавать отдельный frontend-сервис. Spring MVC-контроллер формирует модель данных и возвращает имя HTML-шаблона.

Основные страницы:

- `/login` — авторизация сотрудника.
- `/clients` — поиск и список клиентов.
- `/clients/new` — регистрация клиента.
- `/clients/{id}` — карточка клиента.
- `/clients/{id}/edit` — редактирование данных клиента.
- `/clients/{id}/accounts` — счета клиента.
- `/accounts/{id}/transactions/new` — финансовая операция.
- `/clients/{id}/requests` — обращения клиента.
- `/reports` — отчёты для менеджера или администратора.

## Вспомогательные сервисы на Kotlin

Kotlin не нужно использовать для критичной финансовой логики: код счетов и переводов остаётся в Java-модулях. Kotlin хорошо подойдёт для небольших независимых сервисов.

- `NotificationService` — уведомления об открытии счёта, переводе или блокировке. На первом этапе сервис может записывать уведомления в журнал.
- `ReportExportService` — экспорт отчётов по клиентам или операциям в CSV/Excel.
- `ClientDataMaskingService` — маскировка персональных данных в журналах, например `+371******12`.
- `ClientDataValidationService` — дополнительная валидация персонального кода, e-mail и телефона.
- `DailySummaryJob` — периодическая задача, собирающая число новых клиентов, операций и заблокированных счетов.

## Деплой через Jenkins на одной VM

В production Compose запускает **один контейнер — Spring Boot**. PostgreSQL, Jenkins и общий Nginx работают на Ubuntu. Банк использует сеть хоста Linux: Spring слушает только `127.0.0.1:18081`, а JDBC подключается к локальному PostgreSQL. Nginx маршрутизирует домен `balticbank.duckdns.org` на этот порт. Другим приложениям назначайте собственный Compose-проект, свободный внутренний порт и виртуальный хост Nginx.

### Первый переход с JAR на контейнер

1. Отправьте изменения в ветку job. Если Docker ещё нужно настроить, один раз на VM из доверенной копии обновлённого репозитория выполните от root:

   ```bash
   bash devops/deploy/authorize-docker.sh jenkins
   ```

   Укажите системного пользователя исполнителя, если он отличается от `jenkins`. Команда устанавливает в `/usr/local/sbin` скрипт, принадлежащий root, и разрешает Jenkins вызывать его через sudo без пароля и аргументов. Стадия **Prepare Docker** сама установит недостающие Docker Engine, Compose и Buildx, включит службу и подготовит каталог деплоя. Новые права группы применяются в этой же сборке без перезапуска Jenkins. На уже подготовленной VM стадия только проверяет окружение. Группа `docker` даёт административный доступ к VM, поэтому запускайте job из доверенной ветки. При изменении привилегированного скрипта обновите его той же командой. Для первого публичного переключения нужны Nginx и Certbot.
2. В клиенте PostgreSQL выберите существующую базу банка или создайте отдельную базу, владельцем которой будет роль приложения. В Jenkins укажите **Secret text** `baltic-bank-db-url`, например `jdbc:postgresql://127.0.0.1:5432/bank`, и **Username with password** `baltic-bank-db`. В новой базе Flyway создаст таблицы; для сохранения пользователей и операций используйте прежнюю базу либо восстановите проверенную копию. Сделайте резервную копию перед обновлением схемы.
3. Запустите **Build Now** в job с меткой `baltic-bank-vm`. Jenkins соберёт образ с JDK 25 и Gradle Wrapper и выполнит тесты с одноразовой тестовой PostgreSQL. Рабочие credentials передаются только при запуске production-контейнера. Пользователи с правами Docker могут читать переменные контейнера. Проверьте контейнер на VM: `curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18081/login/client` должен вернуть 200.
4. Когда готовы направить пользователей на контейнер, из обновлённого checkout от root выполните **один раз** `bash devops/deploy/activate-nginx.sh`. Скрипт сохраняет прежний конфиг сайта в `/etc/nginx/sites-available/baltic-bank.pre-container`, проверяет контейнер и конфигурацию Nginx, переключает домен и проверяет HTTPS. Существующий сертификат используется повторно. Для первого выпуска нужны DNS и доступ извне на порты 80/443. Клиентский вход — `https://balticbank.duckdns.org/login/client`.
5. После проверки входа и данных через публичный домен прежнюю службу JAR можно остановить и отключить: `systemctl disable --now baltic-bank.service`. Затем для следующих релизов достаточно **Build Now**. На время замены единственного контейнера возможен краткий перерыв.

### Диагностика и откат

Контейнер можно найти через `docker ps -a --filter label=com.docker.compose.project=baltic-bank`, журнал — через `docker logs --tail 100 ИМЯ_КОНТЕЙНЕРА`. При сбое проверки pipeline пытается вернуть предыдущий Docker-образ с текущими параметрами подключения. Миграции БД требуют отдельного плана восстановления.

При необходимости вернуть прежнюю установку после переключения убедитесь, что прежний JAR совместим с текущей схемой и база содержит актуальные данные. Запустите `systemctl enable --now baltic-bank.service`, проверьте вход на 127.0.0.1:18080, восстановите сохранённый конфиг сайта, выполните `nginx -t && systemctl reload nginx` и удалите маркер `/opt/baltic-bank/containers/nginx-active`. Если две установки используют разные базы, переключение конфигурации не переносит записи между ними.
